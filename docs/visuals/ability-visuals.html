Ability visuals

Procedural PixiJS v8 visuals for the abilities in docs/ROSTER_DESIGN.md. There are no sprites: everything is drawn with Graphics. Each preview runs the exact code shown under it, looping a scripted timeline. Blue is the caster and red is the target.

How these map onto the renderer contract
  • Every visual is a settings object plus one or more draw(g, frame, settings) functions. The settings go into pixi/botAbilityPresentationDefinitions.js. The draw functions go into pixi/renderers/<type>.js, called from update(ctx) (bot visuals) or from the entity layer for phase visuals.
  • g is a Graphics whose origin is the effect's anchor (the bot centre, or the entity centre), in arena units. The renderer positions it and calls g.clear() each frame.
  • frame.angle is in radians: compassDegreesToRadians(rotation), as in activeVisualFrame. frame.progress is 0→1 through the phase or visual window. frame.elapsedMs drives looping motion. Other fields are named per visual.
  • No Math.random. Variation comes from seededRandom(seed), the helper already in rendererHelpers.js. The helpers below are copies of rotatePoint, rectanglePoints, sectorPoints and seededRandom, with the same signatures. One helper is new: arcPath, because Pixi v8 joins an arc to the previous point unless the path starts on the arc.
  • Rendering never decides gameplay. Every number a visual needs comes from state or the ability contract (hitbox sizes, durations, charges).
